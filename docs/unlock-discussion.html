Unlock / Discussion draft 0.7 / 5 September 2026

The agent's password manager.

Add passwords directly, import them, or connect your existing password manager. Unlock maintains the sessions your agents use—without putting secrets into model context.

Updated direction: passwords and sessions; multiple agent profiles; no per-use approval; cookie handoff to existing browser tools; background renewal; OAuth vault access independent of optional MCP; reusable SSO login contexts. Unlock is an authentication layer, not a browser execution proxy. This is a discussion draft, not an implemented or security-verified system. Library candidates below are not live-doc/version verified.

01 / Product thesis

The useful part of the Link analogy

Borrow the durable vault and autofill model of password managers, plus the reusable setup experience of Stripe Link. Link is not universal website SSO; Unlock still needs agent integrations and legitimate authentication mechanisms on destination services.

Working definition: Unlock is a password and session manager for agents. It stores authentication material or resolves it from an authorized external password manager, then turns it into working sessions within standing access configured by the owner. Replacing the user's existing password manager is optional.

  • Human: adds credentials or sessions, assigns connections to agent profiles, handles unavoidable provider challenges and can revoke access. Ordinary use does not need a fresh approval.
  • Agent developer: integrates one access interface instead of collecting passwords and building session recovery.
  • Unlock: stores authentication material, authorizes its retrieval by configured profiles, and synchronizes session updates. The existing browser harness executes the task.
  • Unbrowse: is the first integration and an execution consumer—not a required dependency for every other framework.

The immediate alternative is manual login, copied cookies and per-framework persistent profiles. The product must beat those on repeat-login friction and trust—not merely offer encrypted storage.

02 / The first useful experience

Passwords and sessions are independent inputs.

A password does not mathematically derive a cookie. Unlock submits it through the provider's login flow; the provider issues authentication state if login and any required challenges succeed. A session may include cookies, tokens and origin/device state, not just a cookie jar.

1Password and NordPass exports are initial import candidates, subject to format-specific validation. A live 1Password connector is an initial integration candidate through its supported automation interfaces; available plans, permissions and runtime support must be verified. Do not assume every password manager exposes an unattended API. Where it does not, offer supported import rather than scraping or bypassing its locked vault.

  • Import experience: choose a source format and file in a trusted import UI/CLI; preview non-secret item metadata, select entries, resolve duplicates, then encrypt and save. Do not silently overwrite an existing credential or merge accounts only because their domains match. Unsupported records are reported without secret values.
  • Import safety: exports can be plaintext. Parse outside the LLM, render metadata as inert text, and exclude raw files and secrets from transcripts, repositories, logs, analytics and error reports. Do not retain uploaded originals; minimize and clean up any temporary copies. Tell the owner to remove their source export when finished rather than claiming guaranteed secure erasure.
  • Live integration: the owner authorizes selected items/vaults once using supported least-privilege credentials. The auth runtime resolves the password privately when needed and injects it into login. The LLM cannot choose arbitrary external item references. If caching is later offered, make its encrypted storage, TTL and revocation behavior explicit and opt-in.
  • Independent session lifecycle: source password rotation is picked up on the next uncached resolution. A changed password may or may not invalidate existing website sessions; provider behavior decides. Connector failure returns source_unavailable or source_auth_required, not a silent stale-password fallback. Disconnecting the source stops further source retrieval; derived cookies may remain valid. On observed source disconnection, default to pausing dependent credential-based renewal and new session delivery until the owner explicitly retains or removes the derived sessions; upstream changes cannot be detected instantly without provider signals.
  • No implicit authority: importing or linking an item does not automatically grant it to every profile or start login jobs across the whole vault. The owner selects profile assignments and maintenance during setup. No per-use approval is added. Passkeys, TOTP seeds, recovery codes and attachments require explicit supported handling, not silent inclusion as ordinary passwords.

Unified path: native/imported credential or live source reference → trusted credential resolver → login/SSO adapter → versioned session store → existing browser-tool wrapper. If a usable session already exists, no password fetch is needed.

Autonomous happy path

  1. The owner provisions an agent profile and assigns its allowed connections once, in settings or configuration. No per-task consent screen is required.
  2. A runtime authenticated as that profile requests a connection. Unlock checks the standing assignment; a model-supplied profile name or task description is not authorization.
  3. A background session maintainer renews eligible connections independently of agent tasks. The wrapper fetches the latest saved cookies through an authenticated Unlock SDK call. Cookie values go to the trusted harness runtime, not into model-visible tool arguments or results. No run-bound execution lease is required.
  4. Before the first authenticated navigation, the wrapper injects those cookies into the selected browser context using its native cookie API. The original browser tool then runs normally. The model sees the ordinary navigation/click results, not the authentication payload.
  5. The wrapper captures relevant rotated/new/deleted cookies and synchronizes them back to Unlock. It does not overwrite a live cookie jar with the same old snapshot before every click.
  6. If authentication fails, a trusted login adapter can inject a saved password outside model context, follow a supported login flow, and capture the new session. Unsupported login or provider challenges return an explicit recovery state. OAuth API access and browser login remain distinct capabilities.
  7. Disabling a profile prevents further retrieval and sync through Unlock. Cooperative wrappers can clear their contexts, but cookies already delivered may remain usable until the provider expires or invalidates them.
The demonstration to aim for: wrap an existing browser toolset, inject an authorized session without changing the agent's navigation calls, capture a rotated cookie, restore the updated state into another supported browser, and prove neither cookie values nor passwords enter the model transcript. Also verify revoked profiles cannot fetch or sync again; do not claim already-exported cookies stop working.

Keep the initial deployment small: a vault/profile service with Postgres and mature key management, a durable renewal-job worker, an SDK, and browser-tool adapters. A database-backed job table can suffice initially. No required browser fleet or website-request proxy. Local versus hosted vault custody is separate from where the customer's browser runs.

Proposed SDK surface: connections.add, imports.preview/commit, sources.connect/disconnect, profiles.assign, sessions.get, sessions.sync, wrapBrowserTools. These names describe a proposed contract, not existing code. Secret-returning methods are runtime APIs, not LLM tools. Wrapping a model-visible “get cookies” call is not sufficient—the authenticated fetch itself must run privately inside the wrapper.

The adapter's lifecycle

  1. Bind: map the authenticated profile and connection to a dedicated browser context. Two accounts on the same service must not accidentally share one cookie jar.
  2. Hydrate: import matching cookies once on context initialization/recovery, preserving domain/host-only semantics, path, expiry, Secure, HttpOnly, SameSite and partition metadata when supported. Use native APIs such as Playwright context cookie APIs or CDP—not document.cookie or a universal Cookie header.
  3. Delegate: call the original browser tool with its normal arguments; website traffic goes straight from the browser to the service.
  4. Sync: capture only the selected connection's relevant updates, including deletion/expiry, at supported mutation or persistence boundaries. Use revisions and conflict handling; do not merge unrelated profiles or let stale snapshots resurrect revoked/deleted state.
  5. Recover: on a verified authentication failure, use supported refresh or private password injection, then recapture state. Do not blindly replay a potentially side-effecting action after re-login.

Background session maintainer

Session storage is active, not just a saved cookie jar. A background worker keeps configured, supported connections ready even while agents are idle. This authentication-only worker does not execute agent tasks or proxy browser traffic.

  1. Schedule: track renewal method, session revision, last verification, known provider expiry, next check, runtime affinity and retry state. Renew shortly before known expiry with jitter; where expiry is unknown, use bounded provider-specific health checks and on-use recovery. Cookie expiry alone is not proof of server-side validity.
  2. Renew: prefer a supported refresh flow. Otherwise use a configured SSO context through the destination's normal login redirects, or resolve the current native/imported/external password through a private per-site auth recipe: approved login origin/endpoint, CSRF/bootstrap steps, credential submission, capture of Set-Cookie and required token state, and expected-account verification. Do not assume every service accepts a username/password POST. Google OAuth refresh renews API tokens, not Google browser cookies.
  3. Place: use an HTTP worker where the login flow and session portability support it. For browser/device-bound authentication, run the renewal recipe in the associated trusted harness environment; a central server cannot manufacture missing device state. An offline required runtime is an explicit unavailable state.
  4. Commit: serialize renewal of the same underlying session/refresh-token family, coordinate account-level login budgets, and atomically publish a verified new revision. Concurrent wrapper writes cannot overwrite newer state. Recheck maintenance authorization before committing; disabling maintenance or revoking/deleting a connection stops jobs and rejects stale in-flight results.
  5. Distribute: wrappers receive a revision-only notification or check the revision on their next safe lifecycle boundary, then privately fetch and install updated cookies. Renewing the vault does not automatically update an already-running browser. Avoid replacing cookies during in-flight operations; coordinate providers where a new login invalidates an old session.
  6. Fail explicitly: transient errors use bounded backoff; bad credentials, MFA, CAPTCHA or unsupported login return a challenge/reconnect state without repeated login attempts. Session-only connections cannot fall back to a password that was never stored. Explicit owner sign-out/maintenance disable must not be undone by automatic re-login.

Two recovery paths, one coordinator: scheduled renewal keeps sessions ready; a wrapper reporting a real authentication failure requests the same renewal job rather than starting a competing login loop. Never blindly replay a side-effecting task after authentication recovery.

Terminology: an Unlock account contains agent profiles. A connected website account can be assigned to several profiles. Those profiles isolate local state and authority inside Unlock; they are not automatically separate identities or permission roles at the website.

04 / Where the promise can break

Security guarantees must match the access mode.

  • Cookies are credentials. Giving a framework a cookie jar or unrestricted CDP endpoint delegates substantial account authority. Hiding the password does not make that delegation narrow.
  • Injection must happen outside model-visible tools. The wrapper resolves the selected connection through a privileged SDK call, validates its destination and injects cookies via the browser's cookie API. Password injection, when needed, happens in an auth routine with model observation/recording paused. Authentication payloads and runtime credentials must not appear in model arguments/results, screenshots, traces, process arguments or logs.
  • The harness is trusted, not sandboxed by Unlock. Arbitrary JavaScript, CDP, filesystem access or network inspection can expose credentials. This architecture keeps secrets out of the normal LLM data path; it does not guarantee confidentiality against a hostile model with unrestricted access to the same runtime. Integrators must restrict cookie/credential inspection tools if they require that stronger boundary. A masked password field alone is insufficient.
  • Cookie handoff is the chosen product contract. Actual cookie values are intentionally delivered to an authorized runtime. They carry upstream account authority, not narrower permissions invented by Unlock. This is not an execution gateway, and withholding the password does not prevent misuse of granted session access.
  • “Read-only” is not a label. Enforce it using supported provider scopes or verified operation adapters. Arbitrary browser control does not become read-only through a prompt, an HTTP-method filter or a hostname allowlist. Some permitted reads can also expose sensitive credentials or recovery material.
  • Revocation stops future delivery, not existing cookies. Unlock rejects future fetch/sync calls for the revoked profile. Cooperative adapters may clear their local contexts, but cannot erase other copies. Already-delivered cookies can remain valid until provider expiry/invalidation; provider logout can also affect other profiles sharing that session. The UI must distinguish revoking Unlock access from logging out the upstream account.
  • Sessions do not refresh universally. Respect absolute expiry, token rotation, device binding and server-side invalidation. Try supported refresh, then saved-credential login when permitted; surface a challenge only when needed. Never promise perpetual login or automated MFA/CAPTCHA bypass. Storing a TOTP seed would be a separate explicit decision that concentrates both factors in one trust boundary.
  • Portability is best-effort. Some services need localStorage/IndexedDB, CSRF state, compatible partitioning or device-bound keys in addition to cookies. IP/device changes can invalidate a session. Start with a published cookie-compatible service/browser matrix; do not claim universal session transfer.
  • Vault custody is explicit. Encryption at rest with server-accessible keys is not zero knowledge. The vault's key-custody model and the recipient harness are separate trust decisions. Cookie injection does not require Unlock to host browser execution.
  • Autonomy is standing authorization, not absent authorization. No per-use approval by default. Only the owner/control plane can create profile assignments or broaden access; destination content and model instructions cannot. Authenticate runtimes independently of supplied profile IDs. Any setup/challenge links must be request-bound and must not silently authorize access when opened. Use standard OAuth protections where applicable.
  • Isolation includes the plumbing. Tenant/profile authorization for every vault fetch/write, secure runtime authentication, destination validation for secret injection and profile-specific browser contexts are part of the contract. Any server-side URL fetch needs SSRF protection. Never harvest unrelated browser cookies into a connection.
  • Audit coverage is bounded. Unlock can reliably record vault fetch/sync/revocation events. It cannot claim a complete or independently enforced audit of every website action when the browser communicates directly; wrapper-reported action metadata is supplemental and must be redacted.

Session recovery: validate → reuse; otherwise supported refresh → credential login → challenge/reauth required, skipping unavailable methods. Keep explicit revoked and error outcomes. Serialize refreshes, persist rotated state atomically and coordinate credential-login attempts across profiles; concurrent agents must not overwrite newer state or lock out the account.

06 / A bounded candidate MVP

Prove reconnection is unnecessary—not that every site works.

In: passwords and sessions as independent inputs; native entry, one validated password-import format and one verified live password-manager connector as initial delivery targets; one vault deployment and initial browser-tool adapter; Unbrowse as first consumer; three user-selected services; connection/profile settings; encrypted persistence; cookie retrieval/injection/sync; scheduled background refresh/re-login with per-site auth recipes and bounded retries; on-use recovery; provider challenge handoff; redacted vault audit. OAuth vault access is shared by CLI/SDK and optional MCP. Validate one Google-SSO-to-destination flow before expanding SSO providers. Prove portability with one small second adapter before claiming it.

Out: rebuilding every consumer password-manager feature, universal password-manager compatibility, two-way password synchronization by default, per-task approval prompts by default, universal cookie migration, autonomous signup/email inbox infrastructure, workflow marketplace, arbitrary-site fine-grained permissions, payment execution and “works with every website.” Password storage and use are core, not deferred.

Validation gates

  • Test password-only, session-only, both and neither. Never mark a connection ready just because a secret exists. Verify provider identity after login or session import.
  • Test import with synthetic exports: quoting/encoding, missing fields, multiple accounts on one domain, duplicate conflicts, unsupported records and hostile metadata. Repeated import must not silently overwrite newer passwords. Confirm preview/errors/logs/model requests contain no secrets, originals are not retained and imported items get no implicit profile access.
  • Test the live source path with controlled fixtures: item-level authorization, wrong-tenant/reference denial, password rotation, source outage, locked vault, revoked connector and disconnect during in-flight resolution. Assert no persistent password caching by default and no writes to the source. Test derived-session handling separately from source revocation, without claiming delivered cookies can be recalled.
  • Returning runs under standing access complete without approval clicks. Session state survives restart where supported; measure authentication success without human intervention, time to a usable session and provider challenge frequency.
  • Wrong-account, wrong-tenant and wrong-profile retrieval/sync is denied. Forged profile IDs and agent attempts to assign themselves connections fail. Destination identity matches the owner's configured connection.
  • Revocation blocks the next vault fetch/write, including stale synchronization attempts. Test cooperative cookie cleanup separately; explicitly demonstrate that an already-exported cookie can remain usable without provider invalidation.
  • Trace the full fetch → inject → original tool → capture → sync path. Test normal model-facing output, errors, recordings and telemetry for secret leakage. Document that unrestricted cookie/CDP/filesystem tools defeat isolation against an adversarial agent; do not claim a sandbox the adapter does not implement.
  • Round-trip cookie scope/expiry/flags and supported partition metadata. Test cookie deletion, conflicting revisions, cross-profile account mix-ups, unsupported device-bound sessions and repeated tool calls that must not reset fresh cookies to a stale snapshot.
  • With a fake clock and controlled auth fixtures, verify proactive renewal before known expiry, unknown-expiry health checks, session-only refresh limits, private credential submission, correct-account verification and retry limits. Provider challenges produce explicit recovery states, not retry storms.
  • Race background renewal against wrapper sync, profile revocation and connection deletion. Only the valid newest revision can commit; disabled maintenance never starts a new login. Verify revision propagation into a running wrapper at a safe boundary, including offline-runtime and upstream session-invalidation cases.
  • Exercise OAuth through CLI and HTTP MCP independently: PKCE, exact redirect validation, resource/audience checks, token refresh/revocation and wrong-profile denial. Discovery or client registration alone cannot authorize vault access. A local stdio adapter must not require HTTP-MCP discovery simply to use the shared auth module.
  • For SSO, establish two destination sessions from one explicitly selected identity-provider context; verify each destination account, workspace and assigned profile. Ensure the parent IdP cookies are absent from child task contexts. Test expired parent SSO, first-time consent, account chooser ambiguity and wrong-identity recovery without silently linking accounts.
  • Three prospective users complete their own repeated tasks. Track successful authorized task runs per connected account, reconnect friction and support effort.

Before real production credentials: threat-model review, recovery/deletion design, provider permission/terms checks and independent security testing. Candidate reuse from Unbrowse must be established by code inspection; this discussion did not inspect its implementation.

Privacy constraint: customer passwords, cookies and browsing histories are not a shared data moat. Positioning hypothesis: “1Password helps you sign in. Unlock keeps your agents able to sign in.” This describes the intended job, not a claim that incumbents lack automation capabilities or that every session can be kept alive.

Which browser toolset should we wrap first?

The ownership question is resolved: keep the customer's browser harness. Implement its context binding, privileged cookie import/export and lifecycle hooks without changing the model's normal navigation/click interface.

The installed browser-harness skill documents set_cookies, get_cookies and navigation auto-seeding. These are candidate integration points, not verified implementation evidence. Inspect the code and ensure any existing ambient-cookie auto-seeding cannot override the explicitly selected Unlock account. No live browser or account was accessed for this draft.

09 / OAuth and reusable SSO

One vault authorization layer. Separate destination logins.

OAuth is not an MCP feature to extract. It is an independent authorization protocol that an HTTP MCP integration can use. Put the authorization server and vault resource API below MCP, CLI and SDK adapters. Keep remote MCP optional; do not make the CLI call an MCP server just to retrieve a session.

Three distinct flows

Vault OAuth contract

  • The CLI's proposed unlock login uses the system browser with PKCE and a validated loopback redirect. Device authorization is an optional headless pairing flow, not something every OAuth server supports. Store refresh tokens in an OS keychain/appropriate secret store, never stdout or model-visible tool output.
  • Remote MCP adapts the shared authorization layer to the selected MCP specification's discovery and resource requirements. Validate its exact metadata/client-registration requirements against the chosen spec and SDK before implementation; local stdio MCP need not use the HTTP authorization handshake.
  • Issue tokens for the intended resource and map them server-side to the allowed profile and connection set. Check issuer, audience/resource, expiry and authorization; never accept an arbitrary Google token as an Unlock vault credential or pass an Unlock token to a destination website.
  • Standing authorization avoids per-task prompts. First-time delegation to a new untrusted OAuth client is still a trust decision. Dynamic registration/discovery does not grant vault access; first-party preconfigured clients can reuse owner-defined standing grants.

Reusable Google SSO: one parent, separate destination sessions

  1. The owner signs into Google in an explicitly selected, compatible browser login context, completing required MFA. Persist that context securely; do not assume Google's password login can be automated through a generic endpoint.
  2. A trusted auth adapter starts Site A's normal “Continue with Google” flow in that context. Google may recognize the existing login; Site A still completes its own redirects/callback and creates its own session. First-time consent, account selection or a challenge may require interaction.
  3. Verify Site A's resulting identity/workspace and save only its required session material as a child connection. Repeat Site B's own flow when needed. Do not redeem a code intended for another application's OAuth client or reuse one site's token for another.
  4. Distribute the child site's cookies through the existing wrapper model. Keep Google/other IdP cookies in the private login context by default; they may unlock a much broader set of services than the requested child account.

This can reduce repeated sign-ins across many services using the same Google identity, not create universal access or switch freely among different Google accounts. Separate Google identities need separately bound login contexts. API access/refresh tokens and browser session cookies are different artifacts. A Google OAuth library does not convert a token into arbitrary website login cookies.

Apply the same connector abstraction to Microsoft Entra, Okta and other SSO providers, but validate provider-specific OIDC/SAML flows, consent and browser restrictions. A dependency on Google SSO is a recovery path, not permission to discover or connect every service the user could access.
