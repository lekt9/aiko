# Owner-bound Unlock vault bridge

The agent hosts accept `AIKO_CONNECTOR_VAULT_JSON` from private configuration (local 0600 env or Cloudflare secret). It contains a public HTTPS vault origin and explicit Aiko-owner → vault-runtime assignments:

```json
{
  "origin": "https://YOUR-VAULT-HOST",
  "accounts": {
    "AIKO_ACCOUNT_ID": {
      "token": "OWNER_APPROVED_RUNTIME_TOKEN",
      "tenantId": "VAULT_TENANT_ID",
      "profileId": "VAULT_PROFILE_ID",
      "runtimeId": "VAULT_CLIENT_ID",
      "connections": { "SERVICE_DOMAIN": "VAULT_CONNECTION_ID" }
    }
  }
}
```

This example is a schema guide, not working configuration. The native browser broker requires actual Unlock UUIDs for tenant, profile, runtime and connection IDs. Every cookie domain in a session must map explicitly to that same connection. The runtime token must grant `sessions:read`, `sessions:write`, and `maintenance:request` for the assigned connection. The owner's existing vault credential form, OIDC session and CSRF checks handle password entry. A documented HTTP login recipe or verified imported session is required; arbitrary browser SSO is not implemented by that recipe engine.

Aiko first requires confirmed absence from Arcade. The bridge validates assigned vault metadata, requests the existing renewal job, and opens the vault UI. Completion checks owner/profile/client/connection/domain plus verified session revision and expiry. The connector status bridge never calls credential reveal or retrieves session cookies. The separate trusted browser broker uses the actual Unlock SDK `createVaultAgent` session API, validates the current owner/runtime/domain/revision, and sends only scoped session material through the encrypted VM channel. The runtime token remains on the host. Disconnect disables the Aiko connection and revokes the exact vault runtime session; it does not delete a shared password. Failed remote revocation remains explicitly uncertain.

The browser driver uses the SDK private CDP cookie adapter before its first navigation. Cookie installation and clearing are private host methods, never model tools. Expiry timers, current context generation and revision checks prevent stale reinstall; failed validation clears the scope and blocks navigation/replay. Public domains without an assignment remain public browsing.

Passwords remain inside Unlock’s configured login/renewal recipe. A never-published connection with a recipe can request renewal mechanically; the updated runtime status also marks an expired ready session `renewable`. Revoked, stale and failed sessions are not automatically renewed. Pending renewal blocks authenticated navigation until status proves a new session is ready.

The server adds authenticated session-status and revocation routes to the existing runtime API. Deploy that server revision before enabling the agent bridge. Deployment of this bridge is blocked until a real vault origin and owner-approved mapping are configured. No `password-relay-e2e.json` witness is generated by unit tests or configuration presence.

A real end-to-end witness must exercise the deployed owner's credential/renewal flow, confirm verified status and account isolation, then revoke and verify the session is unavailable. Never put passwords, tokens, cookies, or authorization URLs into the witness.
