# Aiko connector engine

`apps/agent/src/connectors.ts` implements catalog search, owner-bound Arcade authorization, server-side auth polling, tool execution, and evidence-based declarative discovery. `connectors-store.ts` supplies durable private file storage. Actor tools and HTTP/UI integration are owned separately; the shared interface is in `.agent-grid/notes/connector-contract.md`.

Create one engine for the authenticated account, using the existing server account binding. Never accept `owner` from a model argument or request body. The only API-key source is `ARCADE_API_KEY`: Node uses `process.env.ARCADE_API_KEY`; Cloudflare supplies `{env: {ARCADE_API_KEY: env.ARCADE_API_KEY}}`. There is no general API-key constructor argument and no hardcoded credential. An injected fetch is a trusted host transport, not a user-configurable proxy.

```ts
const engine = new ConnectorEngine({
  owner: authenticatedAccountId,
  store: new FileConnectorStore(privateConnectorDirectory),
});
const result = await engine.search("github.com");
// Display the catalog result before choosing a specific tool.
const connection = await engine.connect(result.connectors[0].id);
// Deliver authorizationUrl directly to this owner through the secure UI.
// Poll completeAuth(connection.id); never accept an upstream auth ID from the client.
```

### Adaptive private login rendering

2026-09-08 — User direction: **generate component compositions, not a fixed field-to-layout mapping**. The shared [json-render catalog](../packages/protocol/src/login-ui.ts) defines `LoginStack`, `LoginHeading`, `LoginHint`, `UsernameField`, `PasswordField`, `VerificationCodeField` and `LoginSubmit`. The exported [React registry](../apps/web/src/components/native-login-fields.tsx) implements them. The model chooses grouping, spacing, optional headings/help and the submit label using reviewed literal props; it cannot invent input kinds, arbitrary instructions or executable behavior.

The [metadata-only generator](../apps/agent/src/native-login-render.ts) is mounted on the existing authenticated `/api/connectors/native` path in both Bun and Cloudflare. It uses the host’s native `Infer`, configured model routing and account budget, with no tools or conversation history. Its entire task payload is the sorted field-kind list. Domains, page text, screenshots, usernames, passwords, codes, cookies, challenge IDs and raw request bodies never enter the generation prompt. The renderer’s own schema has no state or built-in actions. Specs arrive in a versioned `layout` envelope with `source: generated` or `fallback`.

Flat keyed specs are outside the native strict-output wire profile, so generation returns JSON text and validates it locally before use. Server and client both enforce strict per-component props and a bounded, complete tree: root stack, at most 18 nodes/depth 4, every observed field exactly once, one submit after the fields, no cycles, shared children, orphan nodes, missing references, values, expressions, state, visibility rules, HTML, URLs or event bindings. In json-render 0.20, multi-component `catalog.validate()` alone does **not** enforce component props; retain the independent validator when extending the catalog. Invalid output never renders partially or reaches another model for repair.

There is at most one native generation invocation per nonempty field combination per owner/renderer lifetime (seven shapes). Concurrent reads coalesce. The HTTP response waits at most 250 milliseconds for presentation, then returns the usable standard JSON-render fallback. Generation continues under its existing 12-second deadline and account budget; the Worker retains this optional work with `waitUntil`. A validated result is cached for later observations, while unavailable inference or invalid output caches the explicit fallback. The open form keeps its current layout so late generation cannot move inputs or erase drafts. This separates form availability from model latency without replacing generated compositions or repeatedly spending on polling. Presentation is pinned for the displayed field/challenge step so regeneration cannot move uncontrolled inputs and erase drafts. A new bound challenge clears the old code; codes allow letters and digits. Recoverable empty/error observations preserve the last unsent DOM inputs disabled, without inventing a password step.

Passwords and codes stay in uncontrolled DOM inputs and the short-lived private submission closure. `LoginSubmit` is a native form button, not a model action. Only the host form handler reads `FormData` and sends `/api/connectors/native`; generated components cannot choose a destination or dispatch a tool. The private runner still rechecks origins, OTP binding, encrypted transport and independent session verification. Provider consent and other consequential private-login controls stay host-owned, outside generation.

**Scope:** this supports the runner’s existing field vocabulary, not arbitrary website forms, security questions, passkeys or CAPTCHA. Adding a field requires matching private discovery and injection support as well as a reviewed catalog component; never ask an LLM to collect missing credentials or bypass a website challenge. See [render/hostile-spec tests](../apps/web/test/native-login-render.test.tsx), [native generator/provider-adapter/API tests](../apps/agent/test/native-login-render.test.ts), and [synthetic browser journey](../apps/web/test/native-login-progress.browser.py). These checks do not establish real-provider login, live model quality or deployment.

The native adapter discovers same-domain navigation links, retaining ordinary query parameters and hash-router paths while excluding credential-bearing URLs and known action/sign-out links. Page evidence and the next route jobs commit in one native Tardigrade effect receipt. The durable frontier deduplicates cycles, survives restart and pause/resume, and binds every queued page to the verified session revision. Revocation or session replacement prevents queued reads from using a different grant. Pending, failed, expired and foreign connections never grant indexing access. The control panel and Telegram status include this work. Coverage describes observed pages, not proof of a complete account crawl: links are read in document order through a fixed CDP DOM program in batches of 256, with remaining batches queued durably using `nextLinkOffset`; hidden routes and button-driven navigation remain unvisited. `linksTruncated` describes an unfinished batch, not a completed site crawl. Adapters without link discovery retain initial-page-only coverage. Network capture renews its bounded observation budget on each navigation. Validated observed capabilities remain discoverable when Arcade is unavailable; an outage still grants no provider-absence fallback or new authorization. Missing context adapters or failed reads are recorded as failures, not completed indexes.

A click on "I'm signed in" does not itself establish success. The runner checks signed-in page markers and secure HttpOnly session cookies, closes login pages, and returns only a bounded verification. Some sites, MFA methods, popup flows, CAPTCHA challenges, and unrecognized signed-in pages still require additional site support; the UI must not claim those connections succeeded. Cookies remain in the owner's existing isolated browser profile. The trusted VM also seals verified login credentials and restorable cookies using Unlock’s `VaultCipher` envelope format in `native_vault` rows of `browser/request-evidence.sqlite`. Its private `browser/unlock-vault.key` is created and fsynced with owner-only permissions; a missing key with existing ciphertext fails closed. Username/password submissions are held only in memory until independent login verification, cleared on cancellation/expiry, and never include one-time codes. The private response reports `credentialsSaved` only when both username and password were captured. Generic screenshot typing cannot claim saved credentials. On the first navigation after driver restart, an unexpired matching vault session can restore cookies through the Unlock SDK’s CDP serialization; missing cookies are restored individually by exact domain, path, and partition while newer browser-profile cookie values are retained. Verification metadata is checkpointed before private-tab cleanup, so completion can retry after the original login tab closes; the connection stays pending and unavailable to agents until cleanup succeeds. Browser actions and authenticated reads now use Unlock SDK `createVaultBridge` to checkpoint the complete app cookie jar after dispatch, including rotations, deletions, partitions and newly created subdomain cookies. Native custody explicitly enables the SDK's descendant-domain scope; other SDK bindings retain exact-domain scope by default. Overlapping native app domains cannot establish separate cookie custody; duplicate connections must be disconnected before sign-in or browser work continues. Cookie revisions use encrypted compare-and-swap independently of login revisions, so rotation cannot extend a verified lease or change continuation identity. A durable `native_cookie_checkpoint` fence is written before dispatch and removed atomically with the encrypted save. If dispatch or saving is interrupted, a future browser cannot restore the old jar: the connection needs fresh verification, and the original action is never replayed. Tests in `apps/agent/test/native-login-vault.test.ts` cover ciphertext reopening, stale writers, revocation, logout, uncertain saves and an opt-in live Chrome test restoring into a different empty context. Disconnect removes this connection’s encrypted vault record. This is VM custody using Unlock encryption and session serialization. Expired native connections renew privately from the verified vault, and an authenticated read receiving an authentication failure may renew and retry that read once. Renewal that encounters MFA stays pending and exposes the owner challenge; it never replays a mutation. Renewal metadata updates the connection record and requeues indexing for the new revision. Request hydration can reopen a stopped browser from the matching saved connection before replay. It accepts ordinary HTML prerequisite reads, but login forms and recognized challenge pages remain blocked. Search reports required route inputs; callers must supply these explicitly, while response-derived identifiers are recomputed by the learned DAG. Password-manager fills use the same multi-step helper. The operator backup API encrypts the VM stores and authoritative account archive into Cloudflare R2; see [backup and recovery](aiko-cloud-backup.md). A separate remote Unlock server is not required by this native deployment. Cancel/disconnect clears the app's browser storage and cookies before releasing the lock. A failed cleanup remains visibly unconfirmed.

Closing an already-removed login tab is accepted only after a fresh browser target inventory confirms it is gone. Other close failures retain the private lock. Sandbox diagnostics record fixed sign-in stages and CDP method names, never arguments or raw errors. ## Legacy tool discovery and availability

Search reads all pages of `/v1/tools?limit=1000&offset=...`, with at most three page requests in flight after the first page. The live engine accepts 1,000 tools per page (8,252 tools in nine requests). It validates `items`, `offset`, stable `total_count`, unique tool identities and metadata. Limits, empty catalogs, malformed responses, unstable pagination, missing configuration, denied access, timeouts, and service errors all return `unavailable`, with `fallbackAllowed:false`. There are no automatic retries of side effects.

Name and task search use a sparse weighted token/BM25 index over toolkit, tool name, and description, with exact toolkit/tool identities ranked first. CamelCase names are tokenized; a qualified name such as `Gmail.ListEmails` is treated as a tool identity. Search returns at most 50 compact matches plus `totalMatches` and `catalogSize`; full schemas are retrieved with `describe(id)`. Domain search uses genuine DNS domains in `metadata.classification.service_domains`, explicit provider scope resource hosts, and documented toolkit/provider mappings, including subdomains. Semantic category labels such as `EMAIL` and `MESSAGING` are retained as metadata, never parsed as website domains. Documented mappings currently cover Gmail/mail.google.com, Slack and GitHub; they establish positive matches only. Absence for a domain requires a complete, nonempty catalog and genuine DNS domain classification on every entry. A positive match can come from a documented mapping even when metadata is absent; those mappings never establish exhaustive absence. The auth-provider listing must also succeed before any absence result can enable fallback. Available auth providers also block browser fallback for matching domains even if they have no executable tools. Unclassified tools make absence uncertain. The result describes the configured Arcade engine catalog, not every catalog visible to every Arcade customer. Pagination cannot prove a transactional catalog snapshot; a count change or duplicate invalidates the read.

`connectBrowser(domain)` and `discover(domain)` independently check the complete cached catalog and provider results. They reuse only unexpired successful snapshots; an expired snapshot must refresh successfully. Only `absent` can permit them. A failed authorization or tool execution never enables browser fallback. Empty catalogs fail closed because an empty configuration cannot establish global service absence.

## Router interface and cache

- `listCatalog(): Promise<ConnectorDescription[]>` returns a defensive copy of all public tool definitions.
- `describe(id): Promise<ConnectorDescription>` returns one tool by its `arcade:<qualified_name>` ID; unknown IDs fail.
- `listAuthProviders(): Promise<ConnectorAuthProvider[]>` returns safe metadata from the official `/v1/admin/auth_providers` listing. A denied, malformed or partial response throws; it is not an empty successful listing.
- Existing `search(query)` adds `totalMatches`, `catalogSize`, `authProviders`, and `authProvidersStatus`. It remains a compact discovery API. A result may be available with no connectors and nonempty authProviders: authorization integration exists, but custom tools are still needed.

`ConnectorDescription` extends the existing connector fields with `toolkit` (name, version, description), `inputSchema`, safe Arcade-native `input.parameters`, structural `requirements`, `metadata`, and `domainEvidence` provenance. `inputSchema` is projected from formatted schemas when present or converted from Arcade value types. An unconstrained Arcade `json` value remains unconstrained JSON rather than incorrectly requiring an object. Parameter names such as `page_token` and secret *requirement names* survive; defaults, credential values, arbitrary configuration extras and auth URLs do not. Requirement statuses describe the catalog snapshot, not an account's completed grant. The router should select a candidate, inspect its schema/requirements, and let the existing authorization/execution APIs enforce actual runtime access.

Auth providers have `{id,providerId,type,status,description,kind:'auth_provider',executable:false,domains,authorizationDomains}`. Authorization origins are hostname-only descriptive metadata, not proof of resource-domain coverage. OAuth endpoint URLs, client IDs/secrets, parameter bags, bindings and grants are omitted. Public provider metadata is separate from tools and cannot be passed to `connect` as an executable connector.

Successful snapshots are cached for five minutes and concurrent requests share one load. Cache scope is transport identity plus SHA-256 of the configured environment key, never the key itself. Account grants/connections remain outside this cache. Key rotation creates a separate scope; an in-flight load pins its original key across every page. At most 16 key scopes are retained per transport. Failed refreshes discard expired snapshots and apply a five-second failure cooldown. Cache consumers receive defensive copies; they cannot mutate the shared definitions. No stale results are used to authorize browser fallback. These caches are process-local; worker isolates each maintain their own cache.

No dependency was added for ranking. The sparse index stores token postings once per snapshot; each query scores posting-list candidates with BM25 and deterministic ties. The catalog parser validates total counts, offsets, page sizes, duplicate identities and page budgets before publishing a snapshot.

## Authorization and execution

Authorization POSTs `{tool_name,user_id}` to `/v1/tools/authorize`. Pending connections durably bind the generated connection ID to account, tool, upstream auth ID, and a ten-minute expiry. `completeAuth` polls `/v1/auth/status?id=...` using only the stored ID and validates returned identity/flow information. Callback query parameters cannot mark a connection connected. Authorization links must use HTTPS on `arcade.dev` or its subdomains.

The provider's completed status enables only the bound tool; `execute` POSTs `{tool_name,user_id,input}` to `/v1/tools/execute`. Reserved identity/auth arguments are rejected. HTTP success alone is insufficient: the response must report `success:true` without an output error or authorization requirement. Provider logs, context, credentials and stack traces are never returned. Value fields are recursively scrubbed for credential keys, known key material and recognized credential strings. This is defense in depth, not a guarantee that arbitrary unlabeled provider data contains no secrets; hosts must keep private tool results within the owning account.

`disconnect` disables this local connection and removes its auth link/flow. It does **not** claim to revoke the upstream OAuth grant. A request already sent cannot be recalled. Connection transitions and execution serialize by account across engine instances in one process. Hosts must enforce a single writer per account across processes, such as a Cloudflare account Durable Object; the file store alone is not a distributed lock.

## Secure browser/password path

After confirmed Arcade absence, a host may inject `secureBrowser.begin({owner,domain,connectionId})`. It must create an owner-bound sign-in relay with credential vault custody and independent browser egress controls. The engine accepts no password and never requests one in chat. Without that adapter the engine reports that secure browser/password connection is not configured. An opened relay produces only a pending connection; this module does not fabricate browser completion or allow browser execution. Relay URLs are host-trusted, HTTPS, owner-only return fields.

## Discovery and durable capabilities

Discovery accepts any syntactically public HTTPS domain. It can read owner-scoped past log projections through `readOwnedLogs(owner,domain)` and exact public GitHub, raw GitHub or DeepWiki evidence URLs. The default public reader reuses `publicTarget`, DNS public-address validation and pinned-IP network requests from existing security code. It refuses credentials in URLs, private/reserved addresses, custom ports and unsafe redirects; it sends no ambient browser cookies or API key to public evidence sites. Custom readers must preserve those protections. Redirected or truncated evidence is not used.

The extractor recognizes explicit `METHOD https://domain/path` endpoint evidence. It rejects cross-domain routes, query strings, fragments and credential-like paths. It never persists request headers, bodies, passwords, cookies or the raw log. Log references are hashed; public evidence retains its cited URL. Records include method/path, source, version, timestamp and `review_required` status, under the owner's namespace. Discovery reloads persisted records after restart. These are candidates, not executable generated code; absence of evidence returns `needs_evidence`. Host log readers must supply authentic owned records, not model-written provenance. This module does not automatically search GitHub or DeepWiki for repositories; callers supply public evidence URLs, while the separate actor capability builder handles its own richer workflow.

`FileConnectorStore` uses owner-prefixed keys, private directory/file modes, no-follow record reads, atomic rename and fsync. Store it outside web roots in a host-controlled private directory. Protect its parent directories and backups; auth links/flow IDs are sensitive and this file adapter does not encrypt at rest. Production hosts can instead implement `ConnectorStore` on encrypted account storage. Never log store records or owner-only auth links.

## Native Arcade production verifier

A direct Google/Slack authorization link alone does **not** remove Arcade's account screen. Arcade's default OAuth apps always use the Arcade user verifier. Production without an Arcade end-user login requires the application's own provider client credentials and a custom verifier; see https://docs.arcade.dev/en/build/user-facing-agents/secure-auth-production.

The Cloudflare host now supplies these routes:

- `/connect/oauth/launch?ticket=...`: accepts a signed, ten-minute, connection-scoped handoff from an authenticated Aiko request; establishes an HttpOnly, Secure, SameSite=Lax browser cookie before redirecting to the saved provider URL.
- `/connect/oauth/callback?flow_id=...`: obtains the Aiko owner from that signed cookie, calls Arcade's server-only `confirm_user` endpoint, checks its returned `auth_id` against the saved grant, then redirects to Aiko's own status page. Query-string user IDs and redirects are never trusted.
- `/connect/oauth/return`: polls the saved authorization and displays success only when Arcade reports completion; provides a return link to Telegram. It never grants general API access from the callback cookie.

The custom verifier redirects to the fixed `/connect/oauth/return` route after confirmation. Authorization deliberately omits `next_uri`: Arcade rejects return URLs that are not configured for the project. In the Arcade Dashboard, choose **Auth → Settings → Custom verifier** and set:

`https://aiko-agent.lewis-6d8.workers.dev/connect/oauth/callback`

For each provider, configure Aiko-owned OAuth client credentials in Arcade and register **Arcade's generated provider callback URL** at Google/Slack/etc. That provider callback is different from Aiko's user-verifier callback above. Do not replace the provider callback with Aiko's verifier URL.

Deployment of these routes alone is not proof that the project uses custom credentials or that the Arcade login screen has been removed. A real end-to-end consent test must confirm the configured provider and verifier after those settings are supplied.


### Rollout flag

`AIKO_ARCADE_OAUTH_ENABLED` defaults to `false` in both production hosts. Until set to exactly `true`, app OAuth is hidden from Connect; new app/tool grants, pending completion and browser verifier routes are disabled. Saved authorization links are omitted. Existing connected accounts can still execute and disconnect; private browser sign-in and Secretary Mode remain available. Deployment explicitly publishes the flag, so an old enabled setting cannot silently persist. Enable only after custom provider credentials, the verifier configuration and end-to-end consent have been verified.


When OAuth is disabled, the frontend silently omits OAuth catalog entries and incomplete OAuth connections and stops polling their pending grants. It does not display an unavailable-feature notice. Already connected accounts retain management controls. Browser sign-in is unchanged; this UI decision does not replace or alter entity-learn request replay.
