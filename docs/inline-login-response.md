# Offer inline sign-in for account tasks

When a requested task needs an unconnected website account, Aiko calls `connector_recommend` with the service name and domain. The existing durable login notification supplies a Telegram **Sign in** button that opens the private connection screen. Aiko should briefly ask the user to sign in there, check the verified connection state, and continue within the user's authorization.

## Shared chat and private-panel controls — 2026-09-09

The foreground actor now mounts `connector_login_start`, `connector_login_status`, `connector_login_advance`, `connector_login_assist`, and `connector_login_cancel` alongside the existing native login component. These controls use the same connector and native operation journal as the private panel and login API. Mutations require the current owned Telegram request; new-origin approval and Google consent remain in the panel. Top-level credential arguments stay rejected on every action.

`start` adopts a standalone panel attempt from validated, contiguous native observations, preserving its attempt ID, challenge and expiry. It replays those existing observations into the native operation projection rather than reopening the page. Conflicting, incomplete, expired or ambiguous receipts hold for reconciliation. The connector checks private status inside its mutation queue before a fresh `begin`, preventing a UI session opened in the meantime from being replaced. A failed status check grants no begin authority.

`status` reads the passive connection snapshot and native journal without opening or renewing the browser. A standalone panel attempt exposes only its ID and expiry; `cancel` can clean up that exact attempt through the existing controller without creating a continuation. Managed-operation cancellation records the request first and reports cleanup separately. A completed connection is not disconnected by this control.

`advance` calls the existing private `form` operation with the pinned attempt. Its response allowlists field kinds, reviewed assistance status, a Google-provider hint and an inert JSON-render layout — the host's metadata-only generative renderer when mounted, the validated catalog fallback otherwise. It discards screenshots, DOM, page URLs, credential values and any injected layout. Provider discovery grants no source access or consent. An already approved assisted flow may progress inside the controller; uncertain tool dispatch is fenced against replay.

### Owner-supplied field injection through chat — 2026-09-09 (owner-directed)

`advance` accepts an optional `fields` wrapper (`username`, `password`, `code`) so the owner can complete a step from chat instead of the panel. The wrapper injects 1:1: only field kinds the fresh private form actually observed are submitted, the attempt is pinned, the OTP submission identity (`challengeId`, `expectedRevision`, `submissionId`) is generated server-side from the displayed challenge — never from model arguments — and username+password rides the existing vault `login` path. Values are never returned, echoed into events, observations or memory, and an uncertain outcome is reported as unknown without resend; the controller owns any retry decision. Accepted tradeoff: values the owner volunteers in chat already sit in that chat turn and the model context; this wrapper adds no new durable copy. Passwords are still safer in the panel, and the tool descriptions say so. `connector_login_assist` starts a Google/email handoff when the owner explicitly chose the method (method plus connected Gmail `sourceConnectionId`); it uses a fresh assistance ID and the controller's existing grant fencing. Google consent and new-origin approvals stay panel-owned — an agent cannot approve them. The web panel renders the same JSON-render layout from the shared catalog and now keeps fields interactive during metadata reads and observation, disabling inputs only while a submission is actually in flight, so slow private browser steps no longer freeze the form.

[Tool and joined-controller checks](../apps/agent/test/capability-builder-login.test.ts) cover both UI-first and chat-first login, challenge preservation, the admission/UI race, unavailable private status, standalone cancellation, and private OTP verification followed by exactly one continuation across native host restart. They also cover injection: username/password rides the engine once, code binds to the displayed challenge, non-observed kinds and approval steps refuse dispatch, lost acknowledgements stay value-free, assist starts with fresh identities, and tool responses carry the generated layout with fallback on renderer failure. Browser transport and Telegram delivery in these checks are fixtures; they do not prove live Google sign-in or deployed behavior. The deployment and evaluation record below predates these controls.

The previous instructions made connector catalog discovery a prerequisite for every login, although the native browser connector already opens a domain directly. They could lead the model to refuse job applications or offer a manual login walkthrough instead of opening the available sign-in screen. The updated actor instructions and tool descriptions distinguish API discovery from native website authentication. Credentials stay in the private login surface; opening that surface does not authorize an application submission or claim a successful login.

The evaluation used Codegraff `deepseek-v4-flash`, the native Cloudflare host adapter, actual code-mode tool dispatch, `connector_recommend`, and durable login notifications. Connection and Telegram transports were fixtures, so no real job application, sign-in, or external message occurred. The API catalog was unavailable in every case. Each case passed only when it invoked the website connection, produced exactly one inline button, and completed the native turn.

| Case | Previous instructions | Updated instructions |
| --- | --- | --- |
| JobStreet application requiring login | No button; deferred the task | One Sign in button |
| Carousell listing requiring login | One Sign in button | One Sign in button |
| LinkedIn applications, held out | One Sign in button | One Sign in button |

The matched runs used the same current tool surface; the actor instructions differed. All three updated cases called the domain login directly. They made 14 model calls in total, compared with 22 for the baseline. This small evaluation is a behavior regression check, not a general quality or latency benchmark. Token totals and billed cost are unavailable. Early fixture runs with a mismatched host or an invalid placeholder authorization origin were discarded.

The 52 targeted regression tests passed, including private sign-in with the catalog available, absent, or unavailable; owner isolation; one inline button across restart; code-mode tool dispatch; and the existing response/model fallback paths.
