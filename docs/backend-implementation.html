UNLOCK / BACKEND & SDK

A persistent vault behind the familiar interface.

The core Node/Postgres service and corresponding SDK are implemented and tested. They are separate from the existing TanStack password-manager demo. This is not a claim of production readiness or universal website authentication.

The existing UI remains synthetic. The new service can hold passwords and sessions when explicitly configured, but no real credentials, production accounts, external account logins, paid APIs or deployment were used during implementation. Work was performed directly, without delegation.

Running the service

Use a patched Node 24 LTS and pnpm 10. The verified environment used Node 24.18.1 and PostgreSQL 17. No deployment is performed by these build commands.

pnpm install --frozen-lockfile
pnpm build:backend
pnpm server:init /private/unlock/server.json
# Edit the private file outside the agent/model context.
UNLOCK_CONFIG=/private/unlock/server.json pnpm server:start

The initializer writes fresh keys with mode 0600, refuses overwrites and does not provision an owner or bypass authentication. Service startup never silently generates replacement keys. The listener binds only to 127.0.0.1 on the configured port (default 4180).

Required operator configuration

  • origin: exact public HTTPS origin, no path. Put a TLS reverse proxy in front of the loopback listener. Preserve the configured Host and strip untrusted forwarded headers. The service pins forwarded scheme/host handling to its configured origin and does not enable CORS.
  • databaseUrl: dedicated least-privilege Postgres credentials. Remote database connections require certificate validation; URL SSL overrides are rejected. Use system CA trust or NODE_EXTRA_CA_CERTS for a private CA.
  • encryption: the generated local keyring, or {"kind":"kms","keyId":"operator-key-ARN","region":"operator-region"}. KMS uses the host's IAM credential chain; grant only the required Encrypt/Decrypt key permissions. Do not put AWS credentials in model arguments.
  • oauth: persisted private signing JWKS and cookie signing keys. Keep old verification keys for their required validity window when rotating.
  • owner: upstream OIDC issuer, client ID, optional confidential-client secret and an exact allowedSubjects list. Register https://your-origin/auth/callback upstream. Confidential clients default to client_secret_basic; set tokenEndpointAuthMethod: "client_secret_post" if required. No owner configuration means owner login is unavailable.
  • recipes: operator-approved fixed-origin JSON/form authentication recipes; configure each login's recipeId and standing maintenance intent explicitly. HTTP recipes reject private/loopback DNS destinations and cross-origin redirects.
  • runtimeId: optional private-runtime affinity identifier for SSO/custom recipes. This is not the OAuth client ID sent by an agent and cannot be selected through an agent request.
{
  "owner": {
    "issuer": "https://your-identity-provider.test",
    "clientId": "your-registered-owner-client",
    "allowedSubjects": ["the-owner's-stable-upstream-subject"]
  },
  "recipes": [{
    "id": "your-approved-service",
    "origin": "https://your-service.test",
    "identityPath": "/documented/session/identity",
    "identityField": "username",
    "loginPath": "/documented/session/login",
    "refreshPath": "/documented/session/refresh",
    "maxSessionMs": 300000
  }]
}

This is a configuration fragment, not a working provider recipe. Paths must come from that provider's reviewed API/flow. Optional bootstrap/CSRF and form encoding are supported. The generic adapter is not an arbitrary-site password form bot, OAuth-token-to-cookie converter or Google browser SSO implementation.

Only explicit localDevelopment: true permits loopback HTTP for local fixtures. Do not expose that mode publicly. Never aim the original web demo or its CSV dialog at real credentials.

Operational limits and recovery

  • 2,000 active logins per vault; 100 profiles/sources/clients and 20 private SSO parents. Five active import previews/receipts. Soft-deleted login metadata is retained; credentials/sessions/assignments/jobs are removed on login deletion.
  • JSON body limit 2 MiB; CSV content 1 MiB; cookie jars 200 entries / 1 MiB, exact domains, Secure cookies. Client response limit 2 MiB. Lists are bounded; owner event/job views return at most 250 records.
  • Access tokens: five minutes. Refresh tokens: seven days. Grants: thirty days. Owner sessions: eight hours; secret endpoints require authentication within fifteen minutes.
  • Worker claim: sixty seconds, verifier/recipe deadline: twenty-five seconds per attempt, at most three transient retries with exponential backoff and jitter. Challenges stop maintenance until explicit owner recovery. Database fencing prevents stale publication; it cannot cancel already-sent upstream requests. Trusted adapters must honor abort signals.
  • Shared private parents serialize authentication across their child accounts. Runtime affinity is fail-closed, not a cross-host dispatcher: deploy the matching trusted worker/recipe environment or surface an unavailable-runtime challenge. No browser execution proxy is introduced.
  • Coarse database-backed rate limit: 600 requests/minute per socket peer. Behind the loopback proxy that is a shared service limit; enforce per-user/IP limits and body/concurrency limits at the edge. Never blindly trust client-supplied forwarding headers.
  • Expired auth/import/OAuth records are collected by the worker. Audit retention is ninety days and completed job retention thirty days. Keep audit logs metadata-only; configure redacted infrastructure logs and disable secret-bearing body/trace/core-dump capture.

Backups and key rotation

Back up Postgres and the required key material separately, using encrypted storage and least-privilege access. A database backup alone is deliberately insufficient to recover secrets. The test suite verifies process restart and key rewrapping; an additional real pg_dump/separate-database restore check verifies credential/session recovery with the retained key. Repeat a full restoration drill with your actual KMS/IAM, proxy and storage setup before production use.

# OFFLINE maintenance: stop every API/worker writer first.
# Add a new active key, retaining the old decryption keys in private config.
UNLOCK_MAINTENANCE_WINDOW=1 UNLOCK_CONFIG=/private/unlock/server.json \
  pnpm server:rewrap
# Verify all restored reads before retiring old keys or backups.

Rewrapping authenticates ciphertext and rewrites wrapped data keys in bounded transactions. It is an operator-controlled offline operation, not an HTTP endpoint or zero-downtime rotation claim. SDK file-token stores have their own encryption keys and cross-process locks; consult the SDK guide before crash recovery or rotation.

Trust model and remaining work

This is server-accessible custody, not zero knowledge. The trusted service process, database integrity, key access and recipe code are part of the trust boundary. Encryption protects stored sensitive values and record binding; it does not make a compromised application or arbitrary database-write privileges harmless. API/module separation alone cannot contain a model with unrestricted shell, file, process or raw-browser access under the credential-owning account.

  • Configuration / authorization: production owner IdP, subject allowlist, TLS, least-privilege database/key access, authorized 1Password account, key backup/rotation and monitoring.
  • Provider-specific code: reviewed browser/SSO recipes for the actual destination services. Google browser SSO, passkeys, MFA, CAPTCHA and device-bound/nonportable sessions are not universally supported. Unsupported/offline flows return challenges, not invented success.
  • Product integration: migrate the existing synthetic vault UI to the authenticated API and a reviewed owner-secret surface. The current UI intentionally has not been silently converted.
  • External validation: live provider/source/KMS integration, production load and failure drills, operational disaster recovery, independent security review and additional browser/platform testing.
  • Revocation: future vault access is blocked; already-delivered cookies and in-flight website requests may remain valid. Upstream logout/revocation needs the provider's own supported mechanism.
