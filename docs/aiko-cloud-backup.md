# Aiko cloud backup and recovery

The Cloudflare account host exposes operator-only `GET /api/control/backups`, `POST /api/control/backup`, and `POST /api/control/restore`, scoped by `?account=<owner>`. Authenticate with the existing operator bearer credential. Ordinary account credentials cannot access these endpoints. Backup is on demand; no scheduled retention or deletion policy is enabled.

Backups require the account and its Codegraff sandbox to be idle. Pending browser observations commit to the authoritative account log before the snapshot. The runner closes its browser, serializes SQLite including committed WAL pages, and transfers bounded chunks through its encrypted private channel. The account archive includes native thread history, entity-learn memory, connection metadata, route frontiers, generated capabilities and saved workflows.

R2 binding `AIKO_BACKUPS` names bucket `aiko-state-backups`. Each chunk and manifest is AES-256-GCM encrypted using `AIKO_BACKUP_KEY`, with owner, snapshot and object location authenticated. Every chunk is downloaded and checked before the encrypted manifest is published. The backup returns HTTP 201 with `status: verified` only after readback. Failed and partial backups never enter the completed-backup list.

`scripts/deploy-aiko-cloudflare.ts` retains the recovery key in the owner-only private deployment configuration and installs it as a Worker secret. Preserve that private configuration independently of the VM and R2 bucket. Redeployment reuses the key. Replacing or losing it prevents recovery of older ciphertext; a backup does not contain its own outer recovery key.

VM files include `owner.json`, the runner journal, request evidence and pointer SQLite stores, and the private native-vault wrapping key. Verified credentials and restorable cookies reside inside encrypted native-vault rows. Browser profile caches, localStorage, downloaded models and executable bundles are excluded. The runtime reinstalls binaries and restores supported sessions from vault cookies or verified login credentials. A site requiring other browser storage may require signing in again.

Restore accepts `{ "id": "<snapshot UUID>", "mode": "vm" }` for native VM state, or mode `account` to additionally import an empty account's archived control-plane state. Recovery verifies all bytes before publication and requires an empty browser store. It refuses to replace populated state. Provision or reconcile the replacement Codegraff VM through the existing operator sandbox controls first. Account import accepts only a fresh account or an exact retry.

Both modes first authenticate and read the bounded `account.json` file, then check its memory erasure checkpoint against current host authority before staging VM files. The same check applies to exact retries. The encrypted manifest is pinned for the transfer, and current authority is rechecked during staging and before publication. Restore and native memory erasure share an owner admission gate; deletion cannot start while the host is publishing an admitted restore.

VM-only recovery requires the live native memory checkpoint to match too. If that journal was lost, restore account memory before restoring the VM. A retained post-erasure checkpoint alone cannot replace the native subject-deletion records: new memory writes are refused until matching history is restored. Missing, foreign or conflicting configured external authority refuses every native write, including writes to an already populated journal; existing rows are not continuing authorization.

Cloudflare records checkpoints through the native memory transaction in a separate host SQL table. That table is outside the memory archive and exported account KV, so restoring either cannot replace it. A fresh recovery target with no local checkpoint requires the trusted application capability `AIKO_MEMORY_RESTORE_AUTHORITY(owner)` to return the current owner-scoped `ErasureFence`; it must come from independent control-plane custody. Missing, foreign or conflicting authority refuses recovery. The capability is an in-process function, not a Wrangler JSON variable, an HTTP argument or a checkpoint copied from the candidate backup. Automatic custody outside the entire account database remains unfinished; do not discard the current authoritative host database assuming R2 alone supplies that checkpoint.

### External authority integration (local, incomplete)

The existing registry now records new-account admission, its initial memory checkpoint and a private per-owner HMAC key in one native SQL/log transaction. The key stays outside account archives and authority events; lost keys are not silently regenerated. Bun can open the same native registry through `openMemoryAuthorityRegistry` at an independent private control-database path. Account membership alone cannot recreate a lost checkpoint, and legacy admission does not invent a zero erasure history. Its writer generation advances only when no claim is pending; an older writer cannot take over after that handoff. This metadata lives outside each account database, but independent deployment, migration and backup of the registry remain operator requirements.

`memory_erase` now **requires** `MemoryBinding.erasureAuthority` and the host owner gate. The binding can be an async resolver so the host obtains independent custody inside the gate for each call. An absent, rejected, empty or foreign resolver cannot fall back to local-only deletion. The tool uses the original native call key and exact receipt key, binds a stable canonical host HMAC to the request and pre-claim native journal/artifacts, and retains its claim before deletion. Cancellation is rechecked before synchronous native deletion. An abort requires the original complete native archive to be verified unchanged; a matching erasure fence, missing receipt, restart or timeout alone cannot release a claim. Aborted operation keys cannot be reused for deletion.

After deletion, `memory_erase({resume})` resolves the original owner-scoped claim and native receipt. It only resumes registered private-result cleanup and exact terminal reconciliation; it cannot delete again. Lost acknowledgements are reconciled against the entire retained event, not just the latest checkpoint. An exact older cleanup completion retains its original fence even after a later erasure; it cannot adopt the newer deletion's identity. A newer deployment can only recover the older committed receipt and clean up: it cannot start the old deletion or abort an operation that might still publish. Writer handoff remains blocked until verified settlement. Completion attests the native live memory store and the registered observation-dependent encrypted result/working-data references actually verified. It does not attest other private copies.

`memoryRestoreAdmission` supplies the existing registry's exclusive restore claim, exact-key checks and read-only settlement reconciliation. New staging is refused without an executor publication reader, while a missing or unknown receipt leaves an existing claim held. Even a settled exact retry must check the current checkpoint and exclude another pending claim. Newer deployments can reconcile an older publication receipt but cannot re-stage under its writer. `nativeMemoryImportPublication` verifies the native account import marker **and** exact current native thread/memory snapshots in the same synchronous read. It can reconcile a native `/control/import` commit after acknowledgement loss and restart without importing again. This reader does not attest account KV or VM/browser publication, and cannot produce a cancellation receipt.

**Shared host integration remains unfinished.** The Cloudflare account and Bun service still need to mount these current external owner/writer and import/publication boundaries. Until then, their native erasure tool is unavailable rather than unfenced. Async registry reads cannot be replaced by a stale process-local checkpoint, and the existing remote backup routes still use their older local checkpoint guard. Account import and both VM restore modes need the same exclusive retained claim, including exact retries. A remote publication terminal additionally needs the executor's verified original-operation publication or cancellation receipt; the current Codegraff restore path generates a new staging identity and accepts only `restored: true`, so it cannot supply that receipt. Do not release an interrupted restore claim, discard the registry, or advertise full recovery safety based on this helper's local tests.

Local verification: `scripts/verify-memory-restore.ts` freezes the current dirty source/dependency closure into one immutable bundle and starts actual local workerd four times. Synthetic tests cover admission rollback on either SQL failure, pending claims across cold restart and complete synthetic account SQLite/KV loss (`deleteAll` on its own Durable Object), writer handoff refusal, unchanged-state abort, cleanup-only recovery, acknowledgement loss, default native-tool refusal without independent authority, canonical linked facts and unrelated encrypted copies. The joined native account-import case loses its SQL commit acknowledgement, cold-restarts workerd into a newer fixture writer, verifies the original native import receipt, settles authority without a second import, and only then permits writer handoff. Fixture, bundle, input hashes, logs and report remain in its printed temporary directory; synthetic database state is removed. This is not a deployed default-host or remote VM publication test.

The current account grant remains authoritative: recovery removes native credentials whose connection, domain or verification revision no longer matches a connected account record. A snapshot cannot reactivate a revoked login. The runner starts a new operation journal; its archived journal is retained for inspection, not replayed as executable work. Verified browser stores publish together by directory rename.

Checkpoint validation prevents an older memory checkpoint from being restored. It does not certify deletion of every archived private copy: historical actor logs, pending private-copy cleanup, untracked KV or browser data, and existing backup objects require their own cleanup and verification. The memory preflight checks archive structure, artifacts and checkpoint equality; actual account memory import additionally verifies the native journal chain. See [selective erasure and its limits](aiko-background.md#selective-memory-erasure).

The owner admission gate excludes concurrent erasure while this host runs a restore. It does not itself provide a durable publication fence for a remote VM command whose host dies before acknowledgement. That recovery boundary needs separate end-to-end verification; a restored SQL checkpoint or a successful controlled VM fixture does not prove it.

Verification is separated by environment: `apps/agent/test/cloud-backup.test.ts` covers encrypted recovery, tampering, SQLite WAL consistency and current-grant filtering; `scripts/verify-cloud-backup.ts` performs a synthetic real-R2 encrypted round trip and deletes its own smoke-test objects. Neither alone proves a production VM recovery. Deployed backup receipts are recorded separately under `artifacts/backups/`.
